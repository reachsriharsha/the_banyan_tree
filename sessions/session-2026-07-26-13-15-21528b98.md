# /ship — Ship a feature end-to-end

Run the full Akshara delivery pipeline for ONE feature with a single burst of questions up front and machine-gated auto-merge. This orchestrates the three existing skills (`vishwakarma` → `nala` → `gargi`) plus the merges and tracker transitions between them. Execute it yourself in the main thread (the sub-skills are workflows, not registered subagents).

## Operating contract (read first)

- **Front-load every decision.** Before any code, gather ALL design + audience decisions in ONE consolidated `AskUserQuestion` round (Phase 0). After that, run **unattended** — do not ask anything else unless a gate fails or you hit a hard safety block.
- **Auto-merge on green.** Merge each PR the moment its gate passes. **NEVER merge on a red gate** — stop and report instead.
- **The gates** (the only things that pause an otherwise-autonomous run):
  | Phase | Gate |
  | --- | --- |
  | Spec | `python3 scripts/tracker.py verify` → `Tracker OK` |
  | Impl | `./test/tools/run_all.sh` — every layer green. A layer may count as passing **only** if its failures are confirmed pre-existing on `main` and untouched by this feature — log that explicitly with the evidence. Otherwise stop. |
  | FAQ | `tracker verify` green |
- **Shell quoting:** write commit messages and PR bodies to temp files; use `git commit -F <file>` and `gh pr create --body-file <file>` (the bash wrapper breaks on parens/apostrophes in `-m`/`--body`). Co-author trailer on commits; plain "Generated with [Claude Code](https://claude.com/claude-code)" trailer on PR bodies — no emoji anywhere (commits, PR bodies, docs).
- Always start each phase from a clean, synced `main` (`git checkout main && git pull --ff-only`).
- Merge with `gh pr merge <#> --merge --delete-branch`.

## Phase 0 — decisions (the one and only question burst)

1. Resolve `feat_id` + MVP story from the argument (e.g. `m1_09_rbac_matrix` / `US-M1-09`). If the tracker shows it already past `Specced`, refuse and report.
2. Read: the MVP story, `backend/rules.md`, `frontend/rules.md`, `backend/log-schema.md`, an existing spec set + FAQ for tone, and the relevant code seams.

4. Ask them ALL in a single `AskUserQuestion` round (≤4 questions; use `multiSelect` to batch sub-choices). Record the answers as a **decision log** to thread through all three phases.

## The command

```bash
cd backend
AKSHARA_CONTROL_DB_URL='postgresql+psycopg://user:pass@prod-host:5432/erp_control' \
  uv run python -m app.dev_db create-super-admin --email you@yourdomain.in --name "Your Name"
```

It's safe to run against production: idempotent on email (re-running prints "already exists — no changes"), one INSERT into `platform_users`, no schema work, no seeding, no tenant touched. That's the whole bootstrap — the super-admin has no tenant, `scope=platform`.

Set `AKSHARA_CONTROL_DB_URL` explicitly. It defaults to `postgresql+psycopg://akshara:akshara_dev@localhost:5432/erp_control`, so without it you'd quietly create the admin in your local DB and wonder why prod login fails.

## Two things you should know before trusting this in production

**1. It lives in a module named `dev_db`, next to a command that drops databases.** `python -m app.dev_db recreate` runs `DROP DATABASE IF EXISTS` on both the control and tenant DBs. Same module, same entry point, one word apart from the command you actually want — with `AKSHARA_CONTROL_DB_URL` pointed at production in your shell. That's a genuinely dangerous adjacency; the production bootstrap path deserves to move out of a `dev_*` module.

**2. There is no migration tooling at all.** I checked: no `alembic/` directory, no `alembic.ini`, and alembic isn't even a dependency in `backend/pyproject.toml`. The root `CLAUDE.md` claims `backend/` contains "alembic migrations" — that's stale.

The control schema is created by `ControlBase.metadata.create_all(control_engine)`, and the only place that runs is **inside `recreate()`, after the drop**. So with the shipped tooling there is currently no non-destructive way to create or evolve the production control schema.

Concretely, `create-super-admin` requires `platform_users` to already exist. On a fresh production database it will fail, and nothing in the CLI will create that table for you without destroying the database first.

## What that means in practice

For a first production deployment you'd need to do one of:

- Run `create_all` yourself against the prod control DSN (a short Python invocation using `ControlBase.metadata`) — works, but it's an undocumented manual step and gives you no upgrade path for the *next* schema change.
- Introduce real migrations before going live.

I'd treat the second as a prerequisite for production rather than a nice-to-have — the first schema change after launch is where the absence really bites, since `create_all` never alters existing tables. That's a plan-level gap worth its own story rather than something to solve in a shell.

**What exists today.** The only way schemas get applied is SQLAlchemy's `create_all` — in `app/bootstrap.py` for the control DB and `provision_tenant` for tenant DBs. `create_all` has one behaviour: it creates tables that don't exist and **silently ignores every table that does**, even if the model has changed. There is no alembic in the repo — no `alembic/` directory, no `alembic.ini`, not even a dependency in `backend/pyproject.toml`. (Root `CLAUDE.md` claims "alembic migrations" exist; that's stale.)

**Why that blocks production.** Day 0 is now solved — bootstrap stands up a fresh install. The block is **day 1**: the first feature you ship *after* go-live that adds a column, a table, or an index has no way to reach the production database. The failure plays out like this:

1. You deploy new code whose model has, say, `students.transport_route`.
2. The production DB, created weeks earlier, doesn't have that column — `create_all` won't add it.
3. Every query touching that model fails with `UndefinedColumn` — a 500 on those endpoints, in production, with real school data you can't drop and recreate.

Dev never feels this because `dev_db recreate` drops and rebuilds from scratch on every run — which is exactly the operation production can never perform. So the gap is invisible in development and absolute in production. It's worse here than in a typical app, because database-per-tenant means one schema change must be applied to the control DB *plus every tenant DB*, transactionally enough that a half-migrated fleet doesn't leave some schools broken.

**What "fixed" looks like** — roughly one story: add alembic with two migration environments (control, tenant), generate the initial baseline from current models, wire `tenant-upgrade-all` to run migrations instead of `create_all`, have bootstrap stamp new DBs at head, and add a CI guard that fails when models drift from migrations (so nobody ships a model change without one).

**Why it can wait until you say so:** it only bites at your first *post-launch* schema change. If you go live and change nothing structural, nothing breaks. But every feature between go-live and adding migrations widens the drift you'll eventually have to baseline — so it's cheapest done before launch, and it's the last genuinely structural item between you and a deployable production.
