## How the Data Flows (Security-Safe Path)

```python
# 1. Parse Excel → Plain strings
raw = _parse_xlsx(raw_bytes)  # Dict with {"siblings": "Raj, Priya"}

    siblings=data.siblings,  # ← Assigned as a Python value

db.add(student)
await db.flush()  # SQLAlchemy generates a parameterized query
```

## Why It's Safe

**SQLAlchemy uses parameterized queries**, not string concatenation:

```python
# SQLAlchemy generates something like this:
# INSERT INTO students (siblings, ...) VALUES (%s, ...)
# with siblings passed as a parameter, NOT concatenated into the SQL string

# Even if siblings contained: '; DROP TABLE students; --
# It would be inserted as a plain string value, not executed as SQL
```

**Key safeguards in place:**

1. **ORM-based** — Uses SQLAlchemy's `Student()` object model, not raw SQL strings
2. **Parameterized queries** — Values are passed separately from SQL, preventing injection
3. **No string concatenation** — The field is never built into a SQL string
4. **Pydantic validation** — Type-checked before reaching the database layer
5. **No eval/exec** — The string is never evaluated as code

## What If Someone Tried Injection?

If an admin filled in siblings with:
```
'); DROP TABLE students; --
```

SQLAlchemy would safely insert it as:
```sql
INSERT INTO students (siblings) VALUES (''); DROP TABLE students; --')
```

The SQL would execute as **a literal string value**, not a command. The `DROP TABLE` would be part of the data, not a separate SQL statement.

## Analogy

It's like putting your data in a locked envelope (parameterized query) instead of writing it directly on the envelope itself (string concatenation). Even if the envelope contains dangerous instructions, they're just text inside — not commands the postal service will execute.

**Verdict**: The `siblings` field is safe from SQL injection. You can confidently allow free-text input.

## Assistant (2026-08-01T05:04:53)

Notice the `_escape_like()` function? Even though Akshara uses ORM, they **still escape LIKE wildcards** because:
- `%` and `_` are SQL LIKE wildcards
- A user searching for "50%_discount" could accidentally use those as wildcards
- Escaping them prevents unintended behavior

## Rules to Stay Safe with ORM

| Do | Don't |
|---|---|
| ✅ Use ORM methods: `.where()`, `.filter()`, `.in_()` | ❌ Use `text()` or `raw()` with f-strings |
| ✅ Pass user input as **values**, not in SQL strings | ❌ Concatenate user input into SQL strings |
| ✅ Use `.ilike()`, `.like()` with `escape` parameter for wildcards | ❌ Trust unvalidated user input in LIKE patterns |
| ✅ Use enums/lists for sort fields (whitelist, not user input) | ❌ Build ORDER BY from user input |
| ✅ Validate/sanitize input **before** using it in queries | ❌ Assume the database will catch everything |

## Example: Safe vs Unsafe Sort

```python
# ❌ UNSAFE — user controls sort field
sort_by = request.query_params.get("sort")  # Could be "name; DROP TABLE"
result = await db.execute(
    select(Student).order_by(text(sort_by))  # Vulnerable!
)

# ✅ SAFE — whitelist approach
ALLOWED_SORTS = {
    "name": Student.name,
    "admission_no": Student.admission_no,
    "roll_no": Student.roll_no,
}
sort_by = request.query_params.get("sort", "name")
if sort_by not in ALLOWED_SORTS:
    raise ValueError("Invalid sort field")
result = await db.execute(
    select(Student).order_by(ALLOWED_SORTS[sort_by])
)
```

## Bottom Line

| Scenario | Risk |
|----------|------|
| **ORM + parameterized queries** | ✅ Very safe (default in SQLAlchemy) |
| **ORM + user input in values** | ✅ Safe (like siblings field) |
| **ORM + `text()` with f-strings** | ❌ **VULNERABLE** |
| **ORM + raw SQL concatenation** | ❌ **VULNERABLE** |
| **Input validation + whitelisting** | ✅ Defense in depth |

**You CAN mostly forget about SQL injection with ORM IF:**
1. You never use `text()`, `raw()`, or `.execute()` with string concatenation
2. You always pass user input as **values**, not SQL strings
3. You whitelist/validate dynamic parts like sort fields
4. You escape wildcards in LIKE queries

**But the moment you do:** `text(f"SELECT * FROM {table_name}")` — you're back to square one with SQL injection.

**Akshara's approach:** Uses ORM correctly + whitelists dynamic fields + escapes LIKE patterns = **very strong protection**. But the developers still follow defensive practices because ORMs are tools, not magic shields.

```python
sc = StudentCreate.model_validate(payload)     # ← Pydantic validation
student = Student(siblings=data.siblings)      # ← ORM object (parameterized)
db.add(student)
await db.flush()                               # ← SQLAlchemy parameterizes
```

## Minor Observations (Not Vulnerabilities)

### 1. LIKE Wildcard Behavior (UX, Not Security)
Some LIKE queries lack the `escape="\\"` parameter:
- `Circular.title.ilike(f"%{search}%")` — users can't search for literal "50%"
- `Staff.name.ilike(f"%{q}%")` — users can't search for "Mr_Smith"

**Risk Level**: None (SQL injection-safe; just unexpected UX)
**Fix Level**: Minor improvement — add `escape="\\"` for consistency

### 2. f-strings Before Parameterization (Safe, But Unusual Style)
```python
Circular.title.ilike(f"%{search}%")  # Safe but looks risky
# vs better style:
pat = f"%{search}%"
Circular.title.ilike(pat, escape="\\")  # Clearer intent
```

**Risk Level**: None (SQLAlchemy parameterizes regardless)
**Fix Level**: Style improvement only
