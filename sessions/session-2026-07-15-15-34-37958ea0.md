## Assistant (2026-07-15T15:35:10)

**What the error is:** WeasyPrint (the library that renders receipt PDFs) failed to load the native C library `libgobject-2.0` at import time. Your seed run got almost all the way through — databases recreated, schemas applied, control and tenant data seeded — and then died at the last step, `_generate_seed_receipts()` in `app/dev_db.py:170`, which calls the real `generate_receipt` service, which lazily imports WeasyPrint at `receipt_pdf.py:125`.

**Why it happens:** WeasyPrint is a Python wrapper over the Pango/GObject C libraries — pip can't install those; they come from Homebrew, and you do have them (`glib 2.88.1`, `pango 1.57.1`, and I confirmed `/opt/homebrew/lib/libgobject-2.0.dylib` exists). The problem is that macOS's dynamic loader (`dyld`) does **not** search `/opt/homebrew/lib` by default — you can see in the traceback it only tried the bare name, `/usr/lib`, and the system cryptex. The project already knows this: `start_api_server.sh:14` exports

```
DYLD_FALLBACK_LIBRARY_PATH="${DYLD_FALLBACK_LIBRARY_PATH:-/opt/homebrew/lib}"
```

so the API server finds the libraries. But you ran `python -m app.dev_db` directly in your shell, where that variable isn't set, so the `dlopen` fails. Activating the venv doesn't help — this is a process environment variable, not a Python path issue. (This is the same root cause as the m3_08 receipt-500 flake noted from earlier sessions.)

**The fix** (when you're ready — not changing anything now): prefix the command with the same variable:

```bash
DYLD_FALLBACK_LIBRARY_PATH=/opt/homebrew/lib python -m app.dev_db recreate --seed
```

One more thing worth flagging: your **second** `recreate --seed` invocation printed no output at all, which means it almost certainly never actually executed (the stray `Display all 206 possibilities?` prompt suggests a tab-completion mishap ate the command). A real run always prints the "Recreating Akshara dev databases" lines. So right now your dev DBs are in the state the first run left them: fully recreated and seeded **except** the seed receipts. Re-running with the `DYLD_FALLBACK_LIBRARY_PATH` prefix will get you a complete seed.

## Assistant (2026-07-15T15:45:04)

The connections you're seeing are not per-table — I checked the actual engine setup in the backend, and here's what's going on.

## Tables don't have connections

A Postgres connection belongs to a *database*, not a table. All 60 tables in `erp_t_dev` are served through the same small set of connections. What actually determines how many connections exist is the number of SQLAlchemy **engines** and their pool settings, and Akshara has exactly these:

| Engine | Created | Purpose |
|---|---|---|
| `control_engine` (sync) | at import, `app/db.py:76` | provisioning / scripts against `erp_control` |
| `dev_tenant_engine` (sync) | at import, `app/db.py:77` | dev-only tenant DB access |
| `control_async_engine` | at import, `app/db.py:82` | request-path tenant resolution |
| one async engine **per tenant DSN** | lazily, `app/tenancy/connections.py:72` | actual tenant traffic (in dev: just one, for `erp_t_dev`) |

So in dev you have at most four engines, regardless of whether you have 60 tables or 600.

## Are connections always open?

No — SQLAlchemy engines are lazy. Creating an engine opens **zero** connections; nothing touches Postgres until the first query runs. What you're likely observing is the pooling behavior *after* traffic:

- Each engine uses the default `QueuePool`: it keeps up to **5 idle connections** warm after use, and can temporarily open **10 more** under load (those overflow ones are closed when returned).
- Once a connection has been used and returned to the pool, it stays open, idle, for the life of the process — there's no idle timeout by default. That's why `pg_stat_activity` shows a handful of `idle` connections per database even when nothing is happening.
- `pool_pre_ping=True` (set on all these engines) means a pooled connection is health-checked with a tiny `SELECT 1` before reuse, so a stale one gets replaced silently rather than erroring.

So the answer to "when the backend comes up, are these connections always present?" is: at startup, none. After the first requests hit each database, a few connections open and then *stay* pooled — which is exactly what you want, because opening a Postgres connection is expensive (a full process fork on the server side, TLS/auth handshake). Pooling is the optimization, not the problem.

## Is this stressing the DB?

At dev scale, not remotely. An idle Postgres connection costs one backend process and a few MB of memory; Postgres ships with `max_connections = 100`, and your dev setup will sit at maybe 5–15 connections total.

The place this *does* become a real design question is production, because of the database-per-tenant architecture: `get_tenant_sessionmaker` creates one engine per tenant DSN, each with its own pool of up to 5 idle + 10 overflow. With 200 active tenants that's potentially 1,000+ pooled connections from a single API process, multiplied again if you run several workers. That's the classic reason multi-tenant setups eventually put **PgBouncer** in front of Postgres or tune `pool_size`/`max_overflow`/`pool_recycle` down per tenant engine. Worth a note for a future milestone, but nothing about it needs action now — and nothing about it has anything to do with the table count.

## What one API call actually does

1. **Tenant resolution** — one query against `erp_control` via `control_async_engine` to look up the tenant's DSN (`connections.py:41`). This result is cached for 60 seconds, so only the *first* request in a minute even does this; the next ones skip it entirely.
