I have a doubt, where does assets are stored?

## Assistant (2026-07-20T14:45:12)

Brand assets are stored **as raw bytes directly in your tenant's Postgres database** — not on disk, not in object storage.

Concretely, in `backend/app/platform/tenant_models.py:97`, the `SchoolAsset` model maps to a `school_assets` table in the tenant DB with `kind` as the primary key (`logo` / `letterhead` / `signature`) and the file content in a `data` bytea column (`LargeBinary`), alongside `content_type`, `size_bytes`, and `filename`. Because `kind` is the PK, there's exactly one current row per asset — uploading again upserts over the old bytes, which is why there's no version history.

The full path: the frontend POSTs the raw file bytes to `/api/v1/admin/settings/assets/{kind}` (no multipart — the body *is* the file, `Content-Type` header carries the MIME type), the service validates kind/MIME/size (2 MB cap) and upserts the row. On display, the browser can't use a plain `<img src>` since the GET needs the Bearer token, so `AssetManager` fetches the bytes and renders an object URL. Receipt PDFs pull the logo and signature straight from this table and embed them as data URIs.

Two deliberate consequences of this design, noted in the model's docstring and the m7_02 spec:

- **No object storage for brand assets yet** — the 2 MB cap and one-file-per-kind make bytea-in-DB fine at this scale, and it keeps tenant isolation trivial (the asset lives in the same per-school database as everything else, so DPDP export/deletion covers it automatically).
- **Contrast with student documents** (m2_07), which *do* go to MinIO/S3 via presigned uploads — those are larger, more numerous, and per-student, so object storage is warranted there.

## What exists today (the real problem)

- `rules.md` already mandates **react-hook-form + zod** with schemas colocated next to forms, and says zod schemas should "mirror Pydantic; eventually generated from OpenAPI."
- In practice there are **two competing patterns**: seven forms do proper zod schemas (fees, auth, academic, platform), while five others (StudentForm, StaffForm, GatewayConfigCard, SchoolProfileForm, import dialogs) use ad-hoc `canSubmit = x.trim() && ...` guards or nothing at all.
- **Regexes are duplicated** — the email regex exists in two places already; money and date patterns likewise.
- Biggest gap: `fetchJson` throws `"422 Unprocessable Entity"` as a literal string and **discards Pydantic's field-level error details**, so backend validation — your actual source of truth — surfaces as a useless message.

## My assessment of the proposal

A giant `src/validations/` folder far from the forms tends to become a dumping ground, and distance from the form makes schema edits error-prone (this is why the colocation convention won industry-wide). But you don't have to choose between "sprinkled" and "one far-away folder." The pattern that fits Akshara:

1. **One `schemas.ts` per feature folder** (`features/<module>/schemas.ts`) holding all zod schemas for that module. This mirrors the backend exactly — every backend module has one `schemas.py` at the HTTP boundary; the frontend feature folder gets the same single validation file. That *is* your "one controlled point per module," just placed where the module lives.
2. **Shared primitives in one file** — `lib/validators.ts` with the email/money/pincode/phone/date building blocks, so rules are defined once and composed per module.
3. **Fix 422 surfacing** — an `ApiError` that parses Pydantic's `detail` so backend errors map onto form fields (`setError`) instead of "422 Unprocessable Entity". This matters more than any folder layout: the backend is the authority (per your thin-client rule), and today its verdicts are invisible.
4. **The endgame your rules.md already names**: generating zod schemas from the FastAPI OpenAPI spec into a `shared/` folder — then frontend validation is *derived* from the backend, and there is literally one control point for the whole system. That's the "novel" approach mature teams use; it can come later without conflicting with steps 1–3.
