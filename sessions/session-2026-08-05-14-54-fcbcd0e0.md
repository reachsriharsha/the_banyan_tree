It fetches `limit + 1` rows (the extra one just detects whether a next page exists) — there's **no `.offset()`**. The next page is a `WHERE (sort_value, id) > cursor_anchor` predicate.

**Frontend** (`features/students/api.ts:74`) uses TanStack `useInfiniteQuery`, sending only `?cursor=...` and rendering a "Load more" button gated on `hasNextPage`. So a school with thousands of students loads only 25 rows initially, then more on demand.

## Why this design is the right call

You intuited the problem correctly — fetching thousands of rows on page load would be bad — but the team chose **keyset over the more common `LIMIT/OFFSET`**, which is actually the better-optimized choice:

- **`OFFSET 10000 LIMIT 25`** forces Postgres to scan and discard 10,000 rows to reach the page. It gets slower the deeper you page.
- **Keyset** (`WHERE (name, id) > (?, ?) ORDER BY name, id LIMIT 25`) jumps straight to the page via an index — constant-time regardless of depth. Ideal for large tenants.

## One thing worth a second look (not a bug, just a trade-off)

The only "fetch everything" path is the **CSV Export** button (`exportStudentsCsv` → `/students/export`), which deliberately streams *all* matching rows with no pagination. That's intentional and correct for an export, but for a genuinely huge tenant it's the one place worth confirming the implementation streams rather than materializing everything in memory at once.

## Possible enhancements (only if you want them)

Since you asked whether it "makes sense to optimize further" — the list itself doesn't need it, but two things you *could* consider later:

1. **Server-side total count** — the UI shows "Load more" but no "1–25 of 4,312". A cheap count query would give that, at the cost of one extra (potentially slow) `COUNT(*)` per filter.
2. **Extract a shared pagination helper** — the keyset logic (`encode_cursor`, `_keyset_predicate`, `build_page`) currently lives only in the students service. When the next large list (fees, attendance) needs the same treatment, it'd be worth promoting to a common module. Right now it's a code-organization point, not a performance one.

Bottom line: your instinct was right, and the codebase already handles it well.
