## Assistant (2026-07-18T11:02:09)

Yes — `recreate` creates the control database too, and it works on a completely fresh Postgres with no extra step.

Here's why, from `backend/app/dev_db.py:84`:

1. `recreate()` calls `_recreate_database(CONTROL_DB_URL)` and then `_recreate_database(DEV_TENANT_DB_URL)` — so both `erp_control` and the dev tenant DB are handled.
2. `_recreate_database` (`dev_db.py:58`) doesn't connect to the target database at all. It connects to the built-in `postgres` admin database on the same host (`_admin_engine`, line 52), then runs `DROP DATABASE IF EXISTS` followed by `CREATE DATABASE`. Since the `postgres` database always exists in any Postgres server, this works even when `erp_control` has never been created — the `IF EXISTS` makes the drop a no-op on first run.
3. After creating both databases it applies the schemas with `ControlBase.metadata.create_all(...)` and `TenantBase.metadata.create_all(...)`, then `--seed` loads the demo data into both.

So for the very first time, the only prerequisites are:

- The Postgres container from `compose.dev.yml` is up (the command connects as the `akshara` user from the default URLs in `app/db.py`).
- For the seed step specifically, MinIO should also be up — the seed issues the two demo receipt PDFs into the object store. If MinIO (or the macOS `DYLD_FALLBACK_LIBRARY_PATH=/opt/homebrew/lib` for WeasyPrint) is missing, it warns and skips the PDFs rather than failing, but receipt downloads will 404 until reseeded.

So the first-time flow is just:

```bash
docker compose -f compose.dev.yml up -d
cd backend
DYLD_FALLBACK_LIBRARY_PATH=/opt/homebrew/lib uv run python -m app.dev_db recreate --seed
```

One caveat: this only creates the control DB and the single dev tenant DB. Additional tenant DBs (`erp_t_<slug>`) are provisioned separately via `python -m app.dev_db tenant-init <slug> --name <name>`.
