```ts
const body: StudentCreate = {

```

`create` is `useCreateStudent()` (`frontend/src/features/students/api.ts:90-97`), a TanStack Query mutation that calls:

```
POST /api/v1/admin/students
```

via `fetchJson` (`frontend/src/lib/api.ts:66-82`), an authed fetch wrapper that attaches the bearer token and retries once on 401. `writeInit` (`api.ts:24-28`) also stamps a fresh `Idempotency-Key: crypto.randomUUID()` header on every write, which the backend requires. ## 3. Backend: router → RBAC → validation → service

`backend/app/modules/students/router.py:374-385`:

```python
@students_router.post("", response_model=StudentOut, status_code=201)
async def create_student_endpoint(
    claims: Annotated[AccessClaims, Depends(requires("students:create"))],
    idem: Annotated[Idempotency, Depends(idempotency_guard)],
    db: Annotated[AsyncSession, Depends(get_db)],
    data: StudentCreate,
) -> StudentOut:
    student = await create_student(db, data, tenant_id=claims.tenant_id or "", as_of=date.today())
    result = serialize_student(student, await get_primary_guardian_out(db, student.id))
    await db.commit()
    await idem.record(jsonable_encoder(result), status=201)
    return result
```

Order matters: `requires("students:create")` runs first (RBAC — 403 + `authz.access.denied` log if the caller lacks the permission), then `idempotency_guard` (replays a cached response if the same `Idempotency-Key` is seen again), then `get_db`, which resolves the caller's tenant and opens a session on *that tenant's own database*.

`data: StudentCreate` is where real validation happens — Pydantic schema (`schemas.py:203-`) with field validators enforcing required/non-blank, length caps, and a `gender ∈ {male, female, other}` enum. A bad payload never reaches the service — FastAPI returns 422 automatically.

## 4. Service — persistence

`create_student` (`service.py:632-641`) orchestrates: resolve academic year → check section exists → check admission number is unique for that year (409 if not) → `_do_create_student` (inserts the `Student` row, decorated `@audit("students.student.created")`) → `_upsert_primary_guardian` (find-or-create `Guardian` by phone, link via `GuardianStudent(is_primary=True)`, and if the guardian has an email with no login yet, provision a parent login) → `generate_admission_invoices` (creates pending fee invoices in the same transaction).

## 5. Where things get written

- `students`, `guardians`, `guardian_students`, `invoices` — all in the **tenant DB** (resolved per-request from `claims.tenant_id`).
- `user_directory` — the one exception: written to the **control DB** only when a parent login is auto-provisioned from the guardian's email.

## 6. Events logged

`students.student.created`, `students.guardian.linked`, `students.guardian.provision_skipped` (email already claimed), plus `authz.access.denied` / `platform.tenant.denied` on failure paths, and `fees.invoice.autogen_skipped` if invoice generation has nothing to do yet.

**End-to-end:** `StudentForm` state → `useCreateStudent().mutate()` → `POST /api/v1/admin/students` (with Idempotency-Key) → RBAC check → idempotency guard → tenant DB session → Pydantic validation → `create_student` service (year/section/uniqueness checks → insert student → upsert guardian → generate invoices) → commit → `StudentOut` JSON back → TanStack Query invalidates the student list, which refetches.
