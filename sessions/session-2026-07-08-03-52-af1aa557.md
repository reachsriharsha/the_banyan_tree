# /ship — Ship a feature end-to-end

Run the full Akshara delivery pipeline for ONE feature with a single burst of questions up front and machine-gated auto-merge. This orchestrates the three existing skills (`vishwakarma` → `nala` → `gargi`) plus the merges and tracker transitions between them. Execute it yourself in the main thread (the sub-skills are workflows, not registered subagents).

## Operating contract (read first)

- **Front-load every decision.** Before any code, gather ALL design + audience decisions in ONE consolidated `AskUserQuestion` round (Phase 0). After that, run **unattended** — do not ask anything else unless a gate fails or you hit a hard safety block.
- **Auto-merge on green.** Merge each PR the moment its gate passes. **NEVER merge on a red gate** — stop and report instead.
- **The gates** (the only things that pause an otherwise-autonomous run):
  | Phase | Gate |
  | --- | --- |
  | Spec | `python3 scripts/tracker.py verify` → `Tracker OK` |
  | Impl | `./test/tools/run_all.sh` — every layer green. A layer may count as passing **only** if its failures are confirmed pre-existing on `main` and untouched by this feature — log that explicitly with the evidence. Otherwise stop. |
  | FAQ | `tracker verify` green |
- **Shell quoting:** write commit messages and PR bodies to temp files; use `git commit -F <file>` and `gh pr create --body-file <file>` (the bash wrapper breaks on parens/apostrophes in `-m`/`--body`). Co-author trailer on commits; 🤖 trailer on PR bodies.
- Always start each phase from a clean, synced `main` (`git checkout main && git pull --ff-only`).
- Merge with `gh pr merge <#> --merge --delete-branch`.

## Phase 0 — decisions (the one and only question burst)

1. Resolve `feat_id` + MVP story from the argument (e.g. `m1_09_rbac_matrix` / `US-M1-09`). If the tracker shows it already past `Specced`, refuse and report.
2. Read: the MVP story, `backend/rules.md`, `frontend/rules.md`, `backend/log-schema.md`, an existing spec set + FAQ for tone, and the relevant code seams.
3. Enumerate EVERY decision the feature needs: backend (tenancy: control vs tenant DB; events; RBAC keys; **external interfaces/providers**; token/cookie/storage choices; money → Decimal boundaries) · frontend (`data-testid` scope) · Gargi **audience** (parent/teacher/school-admin/super-admin).
4. Ask them ALL in a single `AskUserQuestion` round (≤4 questions; use `multiSelect` to batch sub-choices). Record the answers as a **decision log** to thread through all three phases.

## Phase 1 — Vishwakarma (specs)

Follow the vishwakarma workflow, baking in the Phase-0 decisions: write the three dense specs per the `_template` + density rules, `tracker.py init`, `spec/<feat_id>` branch + commit + push + spec PR, `tracker.py spec-pr <#>`. **Gate:** `tracker verify`. Green → merge spec PR + delete branch → `git checkout main && git pull`.

## Phase 2 — Nala (build)

Follow the nala workflow: `impl/<feat_id>` branch, `tracker.py impl-start`, implement per `design.md`, tests per `tests.md` (`test_<feat_id>_*` naming, exact IDs), self-review vs specs (≤3 passes), `./test/tools/run_all.sh` + fix (≤3 passes), write Vyasa impl notes + changelog into the spec dir, commit + push + impl PR, `tracker.py impl-pr <#>`, `tracker.py tests`, `tracker verify`. **Gate:** run_all all green (per the gate rule). Green → merge impl PR + delete branch → `git checkout main && git pull` → `tracker.py merged` → `python3 scripts/release_notes.py` (regenerates `docs/RELEASE_NOTES.md` from the merged changelogs) → commit both `docs/tracking/features.md` and `docs/RELEASE_NOTES.md` in the one `chore(tracker): … → Merged` commit and push.

## Phase 3 — Gargi (FAQ)

Follow the gargi workflow using the Phase-0 audience decision: `faq/<feat_id>` branch, write `docs/specs/<feat_id>/faq_<feat_id>.md` (plain English, dev-internals omitted, honest about not-yet-available capabilities), commit + push + FAQ PR. **Gate:** `tracker verify`. Green → merge + delete branch → `git checkout main && git pull`.

## Done — report

Summarize: the three PR numbers + merge status, each gate's result, final `u/a/e` test counts, the decision log, and anything skipped or blocked (with reason). The tracker row should read `Merged`, and `docs/RELEASE_NOTES.md` should carry the feature's entry (regenerated in Phase 2).

## The only interruptions allowed mid-run

- **A gate is red** (tests fail / tracker drift) — report it precisely; do NOT merge.
- **A hard safety block** (destroying data, reading secrets) — surface and ask.
- **A decision you failed to front-load** — ask just that one, then continue.

Anything else: proceed with the recorded decisions and sensible, spec-documented defaults.

## The core idea: flags gate entry points, not branches

A flag should be consulted at the *boundary* where a capability begins — an endpoint, a dispatcher, a job — and everything downstream stays flag-free. Compare with how RBAC already works here: `requires("fees:read")` appears once per route as a dependency, and no service function ever asks "is this user allowed?". Flags follow the same shape:

```python
# flags.py — the whole public surface
async def flag_enabled(name: str, tenant_id: str | None) -> bool:
    # control-DB lookup: tenant override, else global default; 30s Redis cache

def requires_flag(name: str) -> Depends:      # for whole endpoints
    # 404s when off — the feature "doesn't exist" for that tenant
```

Then the three real placement patterns, using features you already have:

**1. A new endpoint/page dark-launched** — one dependency on the router, zero changes elsewhere:

```python
@router.post("/two-way/reply", dependencies=[Depends(requires_flag("whatsapp_two_way"))])
```

**2. A behavior switch inside an existing flow** — one check at the decision point that *already exists*. The dispatcher is the perfect example: `dispatch_pending` already selects a sender per channel in exactly one place. Per-tenant SMS rollout would be one line there — "flag off → use `PendingSender` regardless of env" — and none of the queueing features (m3_12, m3_16, m4_07, m5_05) ever learn flags exist.

**3. Frontend visibility** — the Sidebar already filters nav items by permission keys from one `usePermissions()` hook. Flags ride the same pattern: one `/api/v1/flags` payload, one `useFlags()` hook, and a component renders or doesn't. The backend check remains the real authority (same comment your `App.tsx` routes already carry about RBAC).

## Why it doesn't metastasize

Two rules keep it to a handful of call sites instead of confetti:

- **A flag guards a capability, not code paths.** If you find yourself checking the same flag in five places, the feature has five entry points — wrong seam. Move the check up to where the capability enters (the route, the dispatcher, the sweep), and let everything below assume it's on.
- **Flags are temporary scaffolding.** A rollout flag exists for weeks: dark-launch → pilot tenant → global on → **delete the flag and the check**. The only long-lived ones are deliberate kill-switches (e.g. `sms_delivery` as an emergency off for a misbehaving provider), and those you *want* permanently at the dispatcher seam anyway.

For scale: rolling out the entire M4 provider stack per-tenant needs roughly three checks total — one in `dispatch_pending`, one on any two-way webhook route, one in the frontend nav. That's the whole footprint. The repo's anti-abstraction rules push the same way — no `FlagProvider` class hierarchy, no decorator zoo; a module with two functions and a singleton cache, like `app/log.py` is for logging.

The one thing worth being strict about in review (and the spec would say so): service-layer functions never call `flag_enabled` mid-computation. If a flag needs to change *how* something computes rather than *whether* it runs, pass the resolved boolean in as an argument from the seam — that keeps the business logic testable without flag fixtures.

## The three parties in DLT

- **Principal Entity (PE)** — the organization in whose name the SMS legally goes out. Registration is a manual, KYC-heavy process on a telecom operator's DLT portal (Jio TrueConnect, Airtel DLT, Vi/Vilpower, BSNL): business PAN/GST, letter of authorization, a fee, and human review that takes days.
- **Registered Telemarketer (TM)** — the aggregator that physically delivers, e.g. MSG91. The PE "chains" the TM's ID in the DLT portal so it may send on the PE's behalf.
- **Operators** — approve headers (the 6-char sender ID like `AKSHRA`) and content templates (bodies with `{#var#}` placeholders). Every SMS is checked at delivery time against the registered template; mismatches are dropped.

## Who does this in Akshara's world

Almost certainly **you, the software provider — not school admins**. Two viable models:

1. **Akshara as the single PE (the practical one)**: you register once, with your header(s) and a generic template set — `absence_alert`, `fee_reminder`, `circular_published` — where school name, student name, amounts are all `{#var#}` variables. 2. **Each school as its own PE**: only needed if a school insists on its own sender ID. That drags every school through portal KYC — realistic only for large institutions, and something you'd offer later, not at MVP.

## Is there a programmatic way?

**Not to DLT itself** — the operator portals have no public submission API; template registration is a human clicking through a web form and waiting for approval. What *is* programmatic: aggregators like MSG91 let you register/sync the *approved* DLT template IDs into their panel (some via API), and their send API then carries `dlt_template_id` per message.
