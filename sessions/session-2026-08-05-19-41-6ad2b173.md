## Why you run out

Assuming all your tenant databases live on **one** DigitalOcean managed Postgres cluster (database-per-tenant = many DBs, one server), the 22-connection cap is **cluster-wide** — every pool counts against it.

Each tenant engine is created with default sizing (`pool_size=5`, `max_overflow=10`). The number that hurts you is **`pool_size=5`**, because those are *persistent* — once a tenant pool has served 5 concurrent requests, it holds up to 5 idle connections and (with `pool_recycle=-1`) never voluntarily gives them back.

| Scenario | Connections held |
| --- | --- |
| Control pools (async + sync, `db.py:81/87`) | ~2–10 |
| 1 tenant at steady state | up to 5 (base), up to 15 under load |
| **10 tenants** at their `pool_size` floor | **10 × 5 = 50** |
| 10 tenants under any concurrency | up to 10 × 15 = 150 |

So **~4 warmed tenants (4 × 5 = 20) + the control pools already exceed 22.** You don't need 10.

## The nuance (so you're not surprised either way)

Pools are **lazy** — they don't grab 5 connections at login. A single parent making one request at a time holds just **1** connection per tenant. So *if* traffic were perfectly serial, 10 tenants ≈ 10–12 connections and you'd survive.

But your React frontend fires multiple fetches per page load (each with its own `client_request_id`), and each concurrent in-flight query checks out a *separate* connection. One parent opening a dashboard can pull 3–5 connections at once. That's what pushes you over — **concurrent in-flight queries, not login count.**

## What to do

Three levers, in order of impact:

**1. Use DigitalOcean's built-in connection pooler (PgBouncer) — the real fix.** DO managed Postgres gives you a *connection pool* endpoint in **transaction mode**. Point your app's DSNs at that. It multiplexes hundreds of app-side connections onto a handful of real backend connections, so 10+ tenants stop competing for 22 raw slots. This is the standard answer for database-per-tenant on a small cluster.

**2. If you stay on direct connections, cap the per-tenant pools.** Right now nothing is set at `app/tenancy/connections.py:72`. Even so, 22 connections ÷ 10 tenants ≈ 2 each is brutally tight and requests will queue (30s `pool_timeout`, then error). Direct connections simply don't scale to 10 tenants here.

**3. Also cap the control pools** (`app/db.py:81/87`) — they default to 5+10 too and are pure overhead you can shrink to 2–3.

## Bottom line (answers the core question)

# /ship — Ship a feature end-to-end

Run the full Akshara delivery pipeline for ONE feature with a single burst of questions up front and machine-gated auto-merge. This orchestrates the three existing skills (`vishwakarma` → `nala` → `gargi`) plus the merges and tracker transitions between them. Execute it yourself in the main thread (the sub-skills are workflows, not registered subagents).

## Operating contract (read first)

- **Front-load every decision.** Before any code, gather ALL design + audience decisions in ONE consolidated `AskUserQuestion` round (Phase 0). After that, run **unattended** — do not ask anything else unless a gate fails or you hit a hard safety block.
- **Auto-merge on green.** Merge each PR the moment its gate passes. **NEVER merge on a red gate** — stop and report instead.
- **The gates** (the only things that pause an otherwise-autonomous run):
  | Phase | Gate |
  | --- | --- |
  | Spec | `python3 scripts/tracker.py verify` → `Tracker OK` |
  | Impl | `./test/tools/run_all.sh` — every layer green. A layer may count as passing **only** if its failures are confirmed pre-existing on `main` and untouched by this feature — log that explicitly with the evidence. Otherwise stop. |
  | FAQ | `tracker verify` green |
- **Shell quoting:** write commit messages and PR bodies to temp files; use `git commit -F <file>` and `gh pr create --body-file <file>` (the bash wrapper breaks on parens/apostrophes in `-m`/`--body`). Co-author trailer on commits; plain "Generated with [Claude Code](https://claude.com/claude-code)" trailer on PR bodies — no emoji anywhere (commits, PR bodies, docs).
- Always start each phase from a clean, synced `main` (`git checkout main && git pull --ff-only`).
- Merge with `gh pr merge <#> --merge --delete-branch`.

## Phase 0 — decisions (the one and only question burst)

1. Resolve `feat_id` + MVP story from the argument (e.g. `m1_09_rbac_matrix` / `US-M1-09`). If the tracker shows it already past `Specced`, refuse and report.
2. Read: the MVP story, `backend/rules.md`, `frontend/rules.md`, `backend/log-schema.md`, an existing spec set + FAQ for tone, and the relevant code seams.
3. Enumerate EVERY decision the feature needs: backend (tenancy: control vs tenant DB; events; RBAC keys; **external interfaces/providers**; token/cookie/storage choices; money → Decimal boundaries) · frontend (`data-testid` scope) · Gargi **audience** (parent/teacher/school-admin/super-admin).
4. Ask them ALL in a single `AskUserQuestion` round (≤4 questions; use `multiSelect` to batch sub-choices). Record the answers as a **decision log** to thread through all three phases.

## Phase 1 — Vishwakarma (specs)

Follow the vishwakarma workflow, baking in the Phase-0 decisions: write the three dense specs per the `_template` + density rules, `tracker.py init`, `spec/<feat_id>` branch + commit + push + spec PR, `tracker.py spec-pr <#>`. **Gate:** `tracker verify`. Green → merge spec PR + delete branch → `git checkout main && git pull`.

## Phase 2 — Nala (build)

Follow the nala workflow: `impl/<feat_id>` branch, `tracker.py impl-start`, implement per `design.md`, tests per `tests.md` (`test_<feat_id>_*` naming, exact IDs), self-review vs specs (≤3 passes), `./test/tools/run_all.sh` + fix (≤3 passes), write Vyasa impl notes + changelog into the spec dir, commit + push + impl PR, `tracker.py impl-pr <#>`, `tracker.py tests`, `tracker verify`. **Gate:** run_all all green (per the gate rule). Green → merge impl PR + delete branch → `git checkout main && git pull` → `tracker.py merged` → `python3 scripts/release_notes.py` (regenerates `docs/RELEASE_NOTES.md` from the merged changelogs) → commit both `docs/tracking/features.md` and `docs/RELEASE_NOTES.md` in the one `chore(tracker): … → Merged` commit and push.

## Phase 3 — Gargi (FAQ)

Follow the gargi workflow using the Phase-0 audience decision: `faq/<feat_id>` branch, write `docs/specs/<feat_id>/faq_<feat_id>.md` (plain English, dev-internals omitted, honest about not-yet-available capabilities), commit + push + FAQ PR. **Gate:** `tracker verify`. Green → merge + delete branch → `git checkout main && git pull`.

## Done — report

Summarize: the three PR numbers + merge status, each gate's result, final `u/a/e` test counts, the decision log, and anything skipped or blocked (with reason). The tracker row should read `Merged`, and `docs/RELEASE_NOTES.md` should carry the feature's entry (regenerated in Phase 2).

## The only interruptions allowed mid-run

- **A gate is red** (tests fail / tracker drift) — report it precisely; do NOT merge.
- **A hard safety block** (destroying data, reading secrets) — surface and ask.
- **A decision you failed to front-load** — ask just that one, then continue.

Anything else: proceed with the recorded decisions and sensible, spec-documented defaults.
