# FastAPI

Official FastAPI skill to write code with best practices, keeping up to date with new versions and features.

## Use the `fastapi` CLI

Run the development server on localhost with reload:

```bash
fastapi dev
```


Run the production server:

```bash
fastapi run
```

### Add an entrypoint in `pyproject.toml`

FastAPI CLI will read the entrypoint in `pyproject.toml` to know where the FastAPI app is declared.

```toml
[tool.fastapi]
entrypoint = "my_app.main:app"
```

### Use `fastapi` with a path

When adding the entrypoint to `pyproject.toml` is not possible, or the user explicitly asks not to, or it's running an independent small app, you can pass the app file path to the `fastapi` command:

```bash
fastapi dev my_app/main.py
```

Prefer to set the entrypoint in `pyproject.toml` when possible.

## Use `Annotated`

Always prefer the `Annotated` style for parameter and dependency declarations.

It keeps the function signatures working in other contexts, respects the types, allows reusability.

### In Parameter Declarations

Use `Annotated` for parameter declarations, including `Path`, `Query`, `Header`, etc.:

```python
from typing import Annotated

from fastapi import FastAPI, Path, Query

app = FastAPI()


@app.get("/items/{item_id}")
async def read_item(
    item_id: Annotated[int, Path(ge=1, description="The item ID")],
    q: Annotated[str | None, Query(max_length=50)] = None,
):
    return {"message": "Hello World"}
```

instead of:

```python
# DO NOT DO THIS
@app.get("/items/{item_id}")
async def read_item(
    item_id: int = Path(ge=1, description="The item ID"),
    q: str | None = Query(default=None, max_length=50),
):
    return {"message": "Hello World"}
```

### For Dependencies

Use `Annotated` for dependencies with `Depends()`.

Unless asked not to, create a new type alias for the dependency to allow re-using it.

```python
from typing import Annotated

from fastapi import Depends, FastAPI

app = FastAPI()


def get_current_user():
    return {"username": "johndoe"}


CurrentUserDep = Annotated[dict, Depends(get_current_user)]


@app.get("/items/")
async def read_item(current_user: CurrentUserDep):
    return {"message": "Hello World"}
```

instead of:

```python
# DO NOT DO THIS
@app.get("/items/")
async def read_item(current_user: dict = Depends(get_current_user)):
    return {"message": "Hello World"}
```

## Do not use Ellipsis for *path operations* or Pydantic models

Do not use `...` as a default value for required parameters, it's not needed and not recommended.

Do this, without Ellipsis (`...`):

```python
from typing import Annotated

from fastapi import FastAPI, Query
from pydantic import BaseModel, Field


class Item(BaseModel):
    name: str

    price: float = Field(gt=0)


app = FastAPI()

```

instead of this:

```python
# DO NOT DO THIS
class Item(BaseModel):

app = FastAPI()


@app.post("/items/")
```

## Return Type or Response Model

When possible, include a return type. It will be used to validate, filter, document, and serialize the response.

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class Item(BaseModel):
    name: str
    description: str | None = None


@app.get("/items/me")
async def get_item() -> Item:
    return Item(name="Plumbus", description="All-purpose home device")
```

**Important**: Return types or response models are what filter data ensuring no sensitive information is exposed. And they are used to serialize data with Pydantic (in Rust), this is the main idea that can increase response performance.

The return type doesn't have to be a Pydantic model, it could be a different type, like a list of integers, or a dict, etc.

### When to use `response_model` instead

If the return type is not the same as the type that you want to use to validate, filter, or serialize, use the `response_model` parameter on the decorator instead.

```python
from typing import Any

from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class Item(BaseModel):
    name: str
    description: str | None = None


@app.get("/items/me", response_model=Item)
async def get_item() -> Any:
    return {"name": "Foo", "description": "A very nice Item"}
```

This can be particularly useful when filtering data to expose only the public fields and avoid exposing sensitive information.

```python
from typing import Any

from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class InternalItem(BaseModel):
    name: str
    description: str | None = None
    secret_key: str


class Item(BaseModel):
    name: str
    description: str | None = None


@app.get("/items/me", response_model=Item)
async def get_item() -> Any:
    item = InternalItem(
        name="Foo", description="A very nice Item", secret_key="supersecret"
    )
    return item
```

## Performance

Do not use `ORJSONResponse` or `UJSONResponse`, they are deprecated.

Instead, declare a return type or response model. Pydantic will handle the data serialization on the Rust side.

## Including Routers

When declaring routers, prefer to add router level parameters like prefix, tags, etc. to the router itself, instead of in `include_router()`.

Do this:

```python
from fastapi import APIRouter, FastAPI

app = FastAPI()

router = APIRouter(prefix="/items", tags=["items"])


@router.get("/")
async def list_items():
    return []


# In main.py
app.include_router(router)
```

instead of this:

```python
# DO NOT DO THIS
from fastapi import APIRouter, FastAPI

app = FastAPI()

router = APIRouter()


@router.get("/")
async def list_items():
    return []


# In main.py
app.include_router(router, prefix="/items", tags=["items"])
```

There could be exceptions, but try to follow this convention.

Apply shared dependencies at the router level via `dependencies=[Depends(...)]`.

## Async vs Sync *path operations*

Use `async` *path operations* only when fully certain that the logic called inside is compatible with async and await (it's called with `await`) or that doesn't block.

```python
from fastapi import FastAPI

app = FastAPI()


# Use async def when calling async code
@app.get("/async-items/")
async def read_async_items():
    data = await some_async_library.fetch_items()
    return data


# Use plain def when calling blocking/sync code or when in doubt
@app.get("/items/")
def read_items():
    data = some_blocking_library.fetch_items()
    return data
```

In case of doubt, or by default, use regular `def` functions, those will be run in a threadpool so they don't block the event loop.

The same rules apply to dependencies.

Make sure blocking code is not run inside of `async` functions. The logic will work, but will damage the performance heavily.

When needing to mix blocking and async code, see Asyncer in [the other tools reference](references/other-tools.md).

## Do not use Pydantic RootModels

Do not use Pydantic `RootModel`, instead use regular type annotations with `Annotated` and Pydantic validation utilities.

For example, for a list with validations you could do:

```python
from typing import Annotated

from fastapi import Body, FastAPI
from pydantic import Field

app = FastAPI()


@app.post("/items/")
async def create_items(items: Annotated[list[int], Field(min_length=1), Body()]):
    return items
```

instead of:

```python
# DO NOT DO THIS
from typing import Annotated

from fastapi import FastAPI
from pydantic import Field, RootModel

app = FastAPI()


class ItemList(RootModel[Annotated[list[int], Field(min_length=1)]]):
    pass


@app.post("/items/")

    return items
```

FastAPI supports these type annotations and will create a Pydantic `TypeAdapter` for them, so that types can work as normally and there's no need for the custom logic and types in RootModels.

No code changes — here's the analysis.

## Is `otp_codes` referred to again after login?

No. The table's only reader is `verify_otp` (`backend/app/auth/otp.py:123`), called from the `/otp/verify` endpoint. Once the code is verified, the flow hands off entirely to the token layer: `tokens.start_session_for` writes a row to `sessions`/`refresh_tokens`, and everything after that — `/refresh`, `/me`, `/logout`, every authenticated request — works off the access JWT and those session tables. The OTP row plays no further role; it's a one-shot entry ticket, not part of the session.

## Why keep it in a database table at all?

The code has a short life, but the state around it needs durability and atomicity:

1. **It works across workers and restarts.** An in-process dict would break the moment you run more than one uvicorn worker (the request lands on worker A, the verify on worker B) or restart the server mid-login.

2. **The lockout state machine needs transactional updates.** The row carries `attempts` and `locked_until`, and `verify_otp` loads it `with_for_update()` (`otp.py:136`) — a row lock so two concurrent verify requests can't both read `attempts=2` and race past the 3-attempt cap. That "read, decide, increment atomically" pattern is exactly what a Postgres transaction gives you cheaply.

3. **The split with Redis is deliberate.** The m1_08 design spec assigns Redis the *request* rate limits (1/min, 5/hr — ephemeral counters where TTL expiry is the feature) and Postgres the *verify* state (`design.md` line 92: "OTP attempt-lockout is separate and lives in Postgres"). If Redis is flushed or restarted you lose rate-limit counters, which is an annoyance; losing lockout state would be a security hole, so it lives in the durable store.

4. **Audit trail.** The rows (with `created_at`, `user_id`, only a SHA-256 hash of the code) double as a history of who requested login codes and when.

## Two things I noticed while checking this (observations only)

- **A code is not invalidated by successful use.** On `Outcome.OK` the row is committed unmutated — nothing deletes it or marks it consumed. Since `verify_otp` always loads the newest row per user, the *same code can be verified again* any time within its 10-minute `expires_at`, minting another session. There's a `_is_replay` helper (`otp.py:73`) that checks `locked_until is not None`, and it's unit-tested in `test_m1_08_otp.py`, but nothing ever calls it in the live path — it looks like an unfinished single-use seam (presumably the intent was to stamp `locked_until` on consume and reject a second use as a replay). The blast radius is small — the attacker would need the plaintext code within its 10-minute window, and refresh-token replay *is* fully handled by family revocation — but it's a real gap versus the usual "OTP is single-use" expectation.

- **Rows are never purged.** Expired rows are harmless for correctness (the query takes the newest per user and checks `expires_at`), but nothing deletes them, so the table grows monotonically with login activity.

If you want, I can flag the single-use gap as a spec/impl follow-up, but per your ask I've changed nothing.

## Assistant (2026-07-19T06:03:50)

Good question — the `family_id` is the piece that makes refresh-token theft *detectable and recoverable*. Here's how it works in `backend/app/auth/tokens.py`, step by step.

## The chain

Every login creates one family, and every rotation stays inside it:

- `/otp/verify` → `start_session_for` mints refresh token R1 with a fresh `family_id` (`tokens.py:136`).
- `/refresh` with R1 → R1 gets `used_at` stamped, R2 is minted **with the same `family_id`** (`tokens.py:187`).
- Refresh again → R3, same family. And so on for up to 30 days.

So a family is the *lineage* of one login on one device: R1 → R2 → R3 → … Exactly one token in the family is "live" (no `used_at`) at any moment; the rest are spent ancestors.

## The attack it defends against

Refresh tokens are the crown jewels — a stolen one grants 30 days of access, versus 15 minutes for an access JWT. Suppose an attacker steals R2 (malware, leaked traffic, a backup of the victim's device):

**Case 1 — victim rotates first.** Victim refreshes with R2 → gets R3. Attacker later presents R2. The lookup at `tokens.py:165` sees `used_at` is already set — that's a replay: two parties provably held the same single-use token. Response: revoke everything (`_revoke_family`, `tokens.py:196`) and log `auth.session.replay_detected`.

**Case 2 — attacker rotates first.** This is the case `family_id` really exists for. Attacker presents R2 first and receives R3′ — a *valid, live* token. The victim's app later presents R2 → replay detected. Now here's the problem: the token that just triggered the alarm (R2) is already dead, and the attacker's R3′ is a different row whose hash you don't know from R2 alone. **The `family_id` is the only link** that lets the server say "kill every token descended from this login" — including R3′ in the attacker's hands. Without it, the attacker keeps a working token for 30 days while the victim just gets a mysterious logout and probably shrugs.

Either way the outcome is the same: the whole family and the session are revoked, both parties get 401, the legitimate user re-authenticates via OTP (mild inconvenience), the attacker is locked out, and there's a loud error-level log for the audit trail.

## Why "revoke the family" and not something narrower?

The core insight: when a replay fires, you *cannot tell which presenter was the attacker* — the request that tripped the alarm might be the victim's. So you can't selectively punish; the only safe move is to burn the entire lineage and force a fresh login. That's cheap here because logging in again is one OTP.

One honest footnote about this codebase: today a family and a session are 1:1 (both created together in `start_session_for`), so `_revoke_family` could technically have filtered on `session_id` instead. `family_id` still earns its place — it names the *credential lineage* explicitly, matches the standard OAuth "refresh token rotation with automatic reuse detection" pattern, and would keep working unchanged if a session ever carried more than one chain (e.g., after a step-up re-auth). `revoke_session` (logout) uses both: it stamps `session.revoked_at` *and* revokes the family, since validity is checked against both.

## Assistant (2026-07-19T11:33:26)

You're right on the first two points, with one important scope correction on the third.

## What's true

- **Family stays constant across refreshes** — yes. The family is assigned once at login (`start_session_for`) and every rotation reuses `token.family_id`.
- **Only one live token per family** — yes. Rotation stamps `used_at` on the old token and mints the successor in the same transaction, under a `SELECT ... FOR UPDATE` row lock (`tokens.py:157`), so even two simultaneous refresh calls can't both succeed — one rotates, the other sees `used_at` set and trips the replay path. At any instant a family has exactly one token with `used_at IS NULL` and `revoked_at IS NULL`.

## The correction: it detects *token sharing*, not *multiple logins*

"One active token" holds **per family, not per user**. If you log in on your laptop and then on your phone, each `/otp/verify` call runs `start_session_for` fresh — two rows in `user_sessions`, two independent families, two live refresh tokens for the same `user_id`, each rotating happily on its own. The system is deliberately fine with that; concurrent logins from multiple devices are normal, legitimate behavior, and nothing in the rotation machinery flags them.

What the family mechanism detects is something narrower and more sinister: **two parties presenting tokens from the *same* lineage**. That can't happen from ordinary multi-device use, because each device has its own family. It can only happen if the cookie was copied out of one browser — i.e., stolen. That's why the response is so drastic (revoke everything): a replay within a family is near-proof of theft, whereas a second login is just Tuesday.

## If you *did* want to detect or limit concurrent logins

The data is already there — you'd query `user_sessions` instead:

- Count rows per `user_id` where `revoked_at IS NULL AND expires_at > now()` — that's the number of live logins.
- The `user_agent` and `ip` columns (captured by `_client_meta` in the router) exist precisely so you could show a "your active sessions" screen or alert on a login from an unfamiliar location.
- A "single-session policy" (new login kicks out old ones) would be a few lines in `start_session_for`: revoke the user's existing sessions before creating the new one. Akshara doesn't do this today, and for a school ERP where a parent might use both a phone and a shared home computer, allowing multiple sessions is probably the right default.

So: rotation + family = "was this credential stolen?", while `user_sessions` = "how many places is this user logged in?" — two different questions answered by two different tables.

There's one dedicated log event for exactly this, and it's already wired in: **`auth.session.replay_detected`**, emitted at **error** level in `rotate_refresh` (`tokens.py:169-177`) at the same moment the family gets revoked. ## What an investigator can reconstruct from it

The record itself only names the who/which-session/which-family. But every Akshara log record automatically carries `request_id`, so you can join it against the `request.start` record of the *same request* — which includes `client_ip` — to see where the replayed token was presented from. And the `user_sessions` row (`session_id` from the log) stores the `user_agent` and `ip` captured at the original login. Together that gives you: which user, which login (when/where/what device), and from what IP the second party presented the stolen token. Because it's `log.error`, it also stands out from the info-level noise — it's the natural thing to alert on.

To hunt for occurrences in the JSON log stream:

```bash
jq 'select(.event == "auth.session.replay_detected")' backend.log
```

## Two caveats worth knowing, since this is a security concern

1. **It can fire on benign traffic.** The check at `tokens.py:165` treats *used* and *revoked* tokens identically. So a stale browser tab retrying `/refresh` after the user logged out (token revoked, not stolen) raises the same `replay_detected` error as a genuine theft. If you ever alert on this event, expect occasional false positives from that path — a real refinement would be logging revoked-token presentation as a separate, lower-severity event.

2. **Detection is where it ends today.** The event is logged and the family is revoked, but nothing notifies anyone — no email to the affected user ("your session was terminated for suspicious activity"), no admin-facing surface, no counter/alarm. For an ERP holding fee-payment data, wiring an alert (or at minimum a super-admin visibility screen) on this event would be a reasonable hardening story to spec later.

Also worth repeating in this context: the OTP-reuse gap I flagged earlier has **no** equivalent log — a second successful verify with the same code just logs a normal `auth.otp.verified`, indistinguishable from the first. So token sharing is loudly detected on the refresh path, and silently invisible on the OTP path. If you want, I can draft these as a small hardening spec (Vishwakarma) when you're ready — but nothing has been changed now.
