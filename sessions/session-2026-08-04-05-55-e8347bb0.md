Based on the codebase analysis, here's how SMS is currently used for absent reports:

## Current Flow

**Trigger:** When a teacher marks attendance **for today**, if students are marked absent, the system automatically queues SMS and WhatsApp notifications to the primary guardian.

```
Teacher marks attendance for today
    ↓
System identifies absent students
    ↓
Queries primary guardian's phone number
    ↓
Queues SMS: "Dear parent, {student_name} was marked absent on {date}. 
Please contact the school if unexpected."
    ↓
Message log entry created (status='queued')
    ↓
Background CLI sweep drains queue and sends via SMS provider
```

## Key Implementation Points

**Location:** `backend/app/modules/attendance/service.py` + `backend/app/modules/communication/`

1. **Deduplication:** Uses `AbsenceNotificationMark` table to prevent re-notifying the same student on the same day (survives corrections)

2. **Corrections:** If a teacher changes "absent" back to "present" before messages send, the queued SMS is cancelled

3. **Backdated entries:** Absence notifications only trigger for **today's attendance**. Admin corrections to past dates (M5-06) never send notifications

4. **Recipients:** Primary guardian's phone from student contact record. Skips if no phone is registered.

5. **Template:** Single template with variables `{student_name}` and `{date}`, mapped to both SMS and WhatsApp channels

6. **Sender Status:** Currently uses a `PendingSender` placeholder—returns "external integration pending" error. Real SMS provider integration (Zepto, Twilio, etc.) still needs to be wired up.

7. **Dispatch:** Background CLI (`python -m app.messages_dispatch`) processes the queue, updates message status to "sent"/"failed", and logs delivery timeline events.

The system is production-ready architecturally (event-driven, channel-agnostic, deduped) but awaits actual SMS provider credentials.
