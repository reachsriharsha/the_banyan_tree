# Akshara log analysis

Reason about the structured JSON logs emitted by the Akshara backend.

## Read first

`backend/log-schema.md` is the contract — read it before answering. It contains:

- the field-by-field schema (mandatory + per-event extras)
- the event taxonomy (`request.start`, `request.end`, `request.failed`, …)
- the correlation rules for `request_id` and `client_request_id`
- baseline jq query examples

If a field, event, or correlation id appears in a log that isn't in `log-schema.md`, the schema doc is stale — flag it.

## Where logs live

Backend logs are JSON, one record per line, on stdout. Local convention:

```bash
./start_api_server.sh > /tmp/akshara-api.log 2>&1 &
```

Then `/tmp/akshara-api.log` is the file. If the user pastes log lines into the chat, work from those. If they reference a path, use it.

## Diagnosis playbook

Work in this order. Skipping steps usually means missing the root cause.

### 1. Pin down the `request_id`

Either the user gives it, or you derive it from a symptom:

| Symptom | Query |
| --- | --- |
| "An error happened recently" | `jq -c 'select(.level == "error")' logs.jsonl \| tail` |
| Specific endpoint failure | `jq -c 'select(.path == "/api/X" and .status_code >= 400)' logs.jsonl` |
| User pastes a UI timestamp | filter on `.ts` range, then on `.path` |
| Frontend report includes a UUID | `jq -c 'select(.client_request_id == "UUID")' logs.jsonl` |

Once you have the `request_id`, the rest of the request's story follows it.

### 2. Pull the full timeline of that request

```bash
jq -c 'select(.request_id == "REQ_ID")' logs.jsonl
```

Expected sequence: `request.start` → handler/module events → either `request.end` (success) or `request.failed` followed by `request.end` with `status_code: 500`. Anything missing is itself a clue (e.g., no `request.end` means the worker died or hung).

### 3. Look at the failure point

If a `request.failed` record exists:

- `exc_type` says what was raised (`RuntimeError`, `IntegrityError`, `ValidationError`, …).
- `traceback` is the full stack as one string. The **last frame whose path contains `/app/`** is your call site — earlier frames are framework/library plumbing.
- Walk back through prior records for the same `request_id` to see what state was reached before the throw.

If `request.end` shows `status_code: 4xx` and there is no `request.failed`, FastAPI converted the failure to a response (validation, auth, HTTPException). Look at the records emitted between `request.start` and `request.end` for the rejection reason.

### 4. Correlate with the UI (if applicable)

If `client_request_id` is **not** `"-"` on the failing record, the frontend's `fetchJson()` assigned that UUID to one specific user action. Querying by it shows every backend log produced by that single click — useful when one button triggers a chain (auth → fetch → submit → notify). If it is `"-"`, the call came from curl/Postman/Playwright/internal cron, not the UI.

### 5. Look for patterns before declaring victory

A single error rarely tells the whole story.

```bash
# Same exception elsewhere?
jq -c 'select(.exc_type == "TYPE")' logs.jsonl |
  jq -s 'group_by(.path) | map({path: .[0].path, count: length})'

# Latency drift on the same path?
jq -c 'select(.message == "request.end" and .path == "PATH") | .duration_ms' logs.jsonl |
  sort -n | awk 'BEGIN{c=0}{a[c++]=why} END{print "p50",a[int(c*0.5)]; print "p95",a[int(c*0.95)]; print "max",a[c-1]}'
```

## jq cookbook

| Question | Query |
| --- | --- |
| All events for one request | `jq -c 'select(.request_id == "X")' logs.jsonl` |
| All events for one UI action | `jq -c 'select(.client_request_id == "X")' logs.jsonl` |
| All errors with traceback | `jq -c 'select(.level == "error") \| {ts,request_id,path,exc_type,traceback}' logs.jsonl` |
| Errors grouped by exception type | `jq -c 'select(.level == "error") \| .exc_type' logs.jsonl \| sort \| uniq -c \| sort -rn` |
| Slow requests (> 1s) | `jq -c 'select(.message == "request.end" and .duration_ms > 1000)' logs.jsonl` |
| Status-code distribution | `jq -r 'select(.message == "request.end") \| .status_code' logs.jsonl \| sort \| uniq -c` |
| One module only | `jq -c 'select(.logger \| startswith("app.modules.fees"))' logs.jsonl` |
| Top callers by IP | `jq -r 'select(.message == "request.start") \| .client_ip' logs.jsonl \| sort \| uniq -c \| sort -rn` |
| Requests with no `request.end` (hung) | `jq -r 'select(.message == "request.start") \| .request_id' logs.jsonl > starts; jq -r 'select(.message == "request.end") \| .request_id' logs.jsonl > ends; comm -23 <(sort -u starts) <(sort -u ends)` |

## Output style

When reporting findings to the user:

1. **Lead with the conclusion in one sentence.** "`/api/students/123` failed with `IntegrityError` because admission_number was duplicated."
2. **Then the trace evidence**: `request_id`, path, `exc_type`, the user-frame `file:line`, and the relevant `extra` fields.
3. **Then the fix**, if obvious from reading the code referenced by the traceback. If not obvious, name what you'd need to look at next.
4. **Do not paste the full traceback** unless the user asks — quote the user-frame line that raised.
5. **Don't speculate past the data.** If a record is missing, say "no `request.end` for this id, so worker likely crashed mid-handler" — don't guess at the cause.

## Out of scope

- **Live tailing.** If the user wants to watch logs in real time, suggest `./start_api_server.sh 2>&1 | jq` in a separate terminal.
- **Code edits.** This skill is read-only diagnosis. Propose a fix in your reply; let the user say "go" before editing.
- **Cross-tenant analysis.** The schema reserves `tenant_id` for future use; until those records exist, all logs are single-tenant.

## When `log-schema.md` is the wrong source of truth

If the user's logs include a field the schema doesn't list, **trust the logs and update the schema in the same change** — `app/log.py` is the emitter, `log-schema.md` is the contract, and they must agree. A contract that lies is worse than no contract.

## Where the ~4 minutes actually go

| Layer | Wall time | Notes |

## Your specific question: unit ∥ e2e

Technically trivially safe — unit tests touch no DB, no server, nothing e2e uses. But it would save **one second**. The instinct (parallelize layers) is right; the target is wrong. The two wins that matter:

## Win 1: parallelize *inside* the API layer (biggest, safest)

The API layer is the whale: 565 tests, one at a time, each spending ~0.2s provisioning its own throwaway tenant (`CREATE DATABASE` + schema + template sync — 56 of 70 test files do this). That per-test isolation is exactly what makes `pytest-xdist` (`-n auto`) a good fit: unique slugs, own DBs, plain `CREATE DATABASE` (no `TEMPLATE` clause, so concurrent creates don't collide in Postgres). Realistic outcome: 135s → ~30–45s. xdist isn't currently a dependency.

Things to verify before adopting it:
- **Shared Redis state** — the OTP limiter and any rate-limit keys are per-email in a shared Redis; tests exercising the same seeded email from two workers could interfere.
- **Control-DB assertions** — any test that counts rows in shared control tables (tenants, audit_of_audits) rather than filtering by its own tenant would flake.
- **Connection budget** — each worker holds engine pools; watch Postgres `max_connections`.

## Win 2: run api ∥ e2e (good saving, one real landmine)

They're independent processes against different databases, and e2e is the only consumer of the browsers. Overlapping them hides the entire e2e layer behind the API layer: total ≈ max(api, e2e) ≈ saves 60–90s.

The landmine: e2e's Playwright `webServer` command starts with `dev_db recreate --seed`, which **drops and recreates `erp_control`**. If API tests are mid-flight against the control DB when that fires, everything dies — this is the same failure family as the "never run two run_all.sh concurrently" note (the `relation tenants does not exist` races). So naive backgrounding of one layer is unsafe; correct shape would be: seed + boot servers first as an explicit step, *then* fork api and the Playwright suite concurrently. Secondary risk: platform e2e specs that list/count tenants would see API throwaway tenants appearing mid-run — worth checking their assertions before committing to this.

## Smaller observations

- **The e2e seed itself** (~40–60s when servers are spawned fresh) is a meaningful chunk of the e2e layer. Reusing servers across runs skips it, but the suite isn't fully rerun-safe against a dirty seed — when I ran the suite 7 times against one seed during the flake hunt, audit-view, message-log, and circulars-inbox eventually failed on accumulated state. So seed-skipping isn't free until those specs pin their state.
- An alternative to xdist for the API layer is module-scoped tenant fixtures (share one tenant per file, ~56 provisions instead of ~565). Bigger architectural change, weakens per-test isolation — xdist gets you more for less risk.

**Bottom line:** unit ∥ e2e ≈ 1s saved. xdist on the API layer plus api ∥ e2e (with the seed hoisted out first) could take the full run from ~4 min to roughly **1.5–2 min**, with the checks above as the homework before flipping either on.

2. **No reports/tracker update.** JUnit/HTML land in `test/reports/e2e/` only when Playwright runs (the reporters are in the config, so you do get them), but `results.jsonl`, the aggregated HTML page, and tracker counts won't refresh — fine for iteration, just run the full gate before a PR.

Also worth knowing: repeated direct runs against one seed accumulate state — the OTP limiter (5/hr on `ravi@example.test`) and the state-sensitive specs (audit-view, circulars-inbox, message-log) will eventually flake without a reseed. A quick reset between long iteration sessions is the seed command itself: `cd backend && DYLD_FALLBACK_LIBRARY_PATH=/opt/homebrew/lib uv run python -m app.dev_db recreate --seed` (plus the redis `del` for the OTP key if you've been running parent-login specs).
