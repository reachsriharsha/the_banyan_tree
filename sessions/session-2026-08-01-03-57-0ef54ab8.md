## Why `sort_order` exists at all

Because class **names don't sort themselves correctly.** The ladder is `LKG, UKG, 1, 2, … , 12`. If you sorted by name:

- String sort: `"1", "10", "11", "12", "2", "3", …, "9", "LKG", "UKG"` — "10" lands before "2", and the kindergarten classes sort to the bottom.
- Numeric sort: doesn't even work — `LKG`/`UKG` aren't numbers.

There's no rule you can derive from the *name* that produces the human order a school expects. So `sort_order` is an explicit integer "display rank" that carries the intended order. The list query is `order_by(sort_order, name)` (`service.py:291`) — rank first, name only as a tiebreaker. That's the whole reason the bulk creator uses the list index (0=LKG, 1=UKG, 2=grade 1…) — the index *is* the pedagogical order.

This is exactly why my earlier point matters: your ranges must keep the **global** index. If "primary" reset to 0, grade 1 would tie with LKG at rank 0.

# Akshara log analysis

Reason about the structured JSON logs emitted by the Akshara backend.

## Read first

`backend/log-schema.md` is the contract — read it before answering. It contains:

- the field-by-field schema (mandatory + per-event extras)
- the event taxonomy (`request.start`, `request.end`, `request.failed`, …)
- the correlation rules for `request_id` and `client_request_id`
- baseline jq query examples

If a field, event, or correlation id appears in a log that isn't in `log-schema.md`, the schema doc is stale — flag it.

## Where logs live

Backend logs are JSON, one record per line, on stdout. Local convention:

```bash
./start_api_server.sh > /tmp/akshara-api.log 2>&1 &
```

Then `/tmp/akshara-api.log` is the file. If the user pastes log lines into the chat, work from those. If they reference a path, use it.

## Diagnosis playbook

Work in this order. Skipping steps usually means missing the root cause.

### 1. Pin down the `request_id`

Either the user gives it, or you derive it from a symptom:

| Symptom | Query |
| --- | --- |
| "An error happened recently" | `jq -c 'select(.level == "error")' logs.jsonl \| tail` |
| Specific endpoint failure | `jq -c 'select(.path == "/api/X" and .status_code >= 400)' logs.jsonl` |
| User pastes a UI timestamp | filter on `.ts` range, then on `.path` |
| Frontend report includes a UUID | `jq -c 'select(.client_request_id == "UUID")' logs.jsonl` |

Once you have the `request_id`, the rest of the request's story follows it.

### 2. Pull the full timeline of that request

```bash
jq -c 'select(.request_id == "REQ_ID")' logs.jsonl
```

Expected sequence: `request.start` → handler/module events → either `request.end` (success) or `request.failed` followed by `request.end` with `status_code: 500`. Anything missing is itself a clue (e.g., no `request.end` means the worker died or hung).

### 3. Look at the failure point

## 1. The invoice tests (m3_07 e3, m3_08 e1) — date-stale fee structure

Both admit a fresh student into **class 5** and rely on admission auto-invoicing (m3_06). But:

- **Today is 2026-08-02.**
- Class 5's **active** structure (`fs_01KZ05Q0…`, v2) has exactly **one installment, due 2026-08-01** — now in the past.

The demo tenant has **26 accumulated students** (a fresh seed has a handful) from prior un-cleaned runs — the harness only prunes `erp_t_e2e-*` throwaways, never the demo tenant. ## Is the date a due date?

**Yes.** When you add a fee-structure version, each **installment (term)** you enter has a **due date** — the date that term's fee is due. It is *not* a "created" or "activated" date. That due date drives real behavior:

| Table | id prefix | What it stores | Key columns |
|---|---|---|---|

Grounded now. Here's the accurate answer — and it hinges on a distinction that's easy to blur.

## First, there are *three* secrets, not one

Akshara stores all three **per tenant** in each school's `gateway_config` row (`models.py:329`):

| Secret | What it's for | Verified where |
|---|---|---|
| `key_id` + `key_secret` | Create the Razorpay order (API auth) **and** verify the browser checkout callback (`order_id\|payment_id` HMAC) | `verify_checkout_signature` uses `key_secret` |
| `webhook_secret` | Verify the server-to-server webhook (`X-Razorpay-Signature` = HMAC of the raw body) | `verify_webhook_signature` uses the tenant's `webhook_secret` |

The webhook URL is `/api/v1/public/webhooks/razorpay/{slug}` — the **slug routes to the tenant**, then the signature is checked with *that tenant's* stored `webhook_secret`.

## Your question: can the same test key/secret serve both DIS and SVS?

**For testing — yes.** You typically have one Razorpay **test** account (one `rzp_test_…` key pair). You can store that same `key_id`/`key_secret` in both DIS's and SVS's gateway config; both create orders in that one test account, and test money is fake so settlement doesn't matter. The checkout callback verifies fine for both (same `key_secret`).

**The webhook secret follows a matching rule, not a sharing rule.** Whatever secret you set on the `.../dis` webhook in the Razorpay dashboard must **equal** DIS's stored `webhook_secret`; the `.../svs` webhook's secret must equal SVS's. You *may* use the same secret for both webhooks (then store that one secret in both configs) or two different ones — either works, as long as each URL's secret matches its tenant's config.

## The gotcha you need to know (one account → cross-delivery)

With **one** Razorpay account and **two** webhook URLs, Razorpay fires **every** payment event to **both** URLs — it has no idea a given payment "belongs to DIS." So a DIS payment's `payment.captured` also lands on your `.../svs` endpoint. What happens there:

- If the two webhooks use **different** secrets → the signature check **fails** at the wrong endpoint → logged as `fees.webhook.rejected`.
- If they share the **same** secret → the signature passes, but SVS then looks for that `order_id` among *its* orders, doesn't find it → rejected/quarantined.

Either way it's **safe** (a foreign payment can never post to the wrong school), but you'll see reject/quarantine noise in the logs. This is inherent to sharing one Razorpay account — which is exactly why the design says *"each school runs its own Razorpay account"* (`webhook_router.py:4`).

## Practical recommendation

- **Quick testing (one account):** reuse the same test key/secret in both tenants, add two webhook URLs, use one shared `webhook_secret` stored in both — and just ignore the cross-delivered rejects. Or, cleanest of all, **test one school at a time** (only one webhook active) so there's no cross-fire.
- **Clean testing:** two separate Razorpay **test** accounts (one per school) — each with its own key/secret and its own webhook. No cross-delivery, mirrors production exactly. More setup (two Razorpay logins).

## Important production caveat

Sharing one key/secret is a **test-only** shortcut. In production each school **must** have its own Razorpay account — that's the whole point of the per-tenant `gateway_config`: money settles into *that school's* bank account, and each account's webhooks only carry its own payments (no cross-delivery). Don't ship two schools pointing at one account.
