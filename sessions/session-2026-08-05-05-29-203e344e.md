DLT template registration is super-admin only — a school admin can't see or do it anywhere in the app.

**Where it lives:** the platform console at `/platform/tenants`, which renders the `SmsTemplates` panel (`frontend/src/features/platform/components/SmsTemplates.tsx`, mounted in `TenantsPage.tsx:15`). That whole route tree is only reachable when the logged-in user has `scope === 'platform'` (`App.tsx:113`) — school users never land there.

**Backend gating** (`backend/app/platform/router.py:184-210`, the m4_01 SMS template registry):
- `GET /api/v1/platform/tenants/{tenant_id}/sms-templates` — requires `platform:tenant:read`
- `PUT .../sms-templates/{template_id}` (paste the operator-approved DLT id, set Draft/Approved/Active/Disabled) — requires `platform:tenant:manage`

A comment in that router states the design intent explicitly: "no school user holds any platform key," and the m4_01 comment says "the super-admin pastes the operator-approved DLT id." This matches the single-PE model — the platform operator owns the DLT relationship with the telco, so schools don't manage registration.

**What a school admin does get:** the tenant-side `GET /api/v1/communication/templates` (gated on `communication:read`, `communication/router.py:144`) returns templates for the notification-map override picker — but its `TemplateOut` schema exposes only `id`, `name`, and `status`. The `dlt_template_id` field is deliberately absent from the tenant-facing schema, and there's currently no school-admin screen that even lists templates (the only consumer surface is the platform console; the communication feature's UI is just `CommunicationPage.tsx` for the message log).

So: school admins can at most indirectly see template *status* via the API; registration and the DLT id itself are platform-console, super-user territory. If you want school admins to see (read-only) which templates are DLT-approved, that would need a new tenant-side surface — likely a small addition to the settings or communication page fed by the existing `/communication/templates` endpoint.

## Assistant (2026-08-05T05:39:22)

I've traced the whole m4_01 pipeline end to end. Here's how the existing system actually works, and then where each of your concerns lands.

## How the existing system works

**1. Bodies live in code, not in any UI.** `TEMPLATE_CATALOG` in `backend/app/modules/communication/catalog.py:46` is the single source of template wording — 5 SMS, 4 WhatsApp, 3 email templates. Creating or changing a body means a code change + code review. This is deliberate per the m4_01 spec: "bodies are canonical by design" and "template CRUD beyond the lifecycle fields" is explicitly out of scope.

**2. Every school gets its own copy of the catalog.** `sync_templates()` materializes the catalog into each tenant's own DB (`sms_templates` table) — automatically at provision time, or via `uv run python -m app.templates_sync <slug>|--all` for existing schools. The sync is insert-missing-only: it never updates existing rows, so a school's DLT id and status survive redeploys. New SMS rows start as `draft`.

**3. The super admin manages lifecycle per school — and that part IS editable.** In the platform console (SMS templates section on the tenants page), the super admin picks a school from a dropdown, then for each template can edit exactly two fields: the **DLT template id** (pasted after manual registration on the operator's DLT portal) and the **status** (`draft → approved → active → disabled`). Activating without a DLT id is rejected with a 422 (`can_activate` at `catalog.py:187`). So "not editable by super admin" is only true of the *body text* — the DLT id and status are editable today, per school.

**4. Dispatch is driven by an event→template map, with per-school overrides.** `DEFAULT_MAP` (`service.py:69`) maps events like `fees.payment.recorded → sms: payment_received`. Each school's DB has a `notification_mappings` table that overlays this: a row can repoint an event+channel to a *different template id* or disable that channel entirely. Only `active` templates are sent; an SMS whose variables don't cover the template's placeholders fails at dispatch with an honest error.

## Mapping this to your concerns

**"SMS will be specific to each school"** — the design intent is the opposite, and it's worth understanding why before changing it. Because Akshara is the *single DLT Principal Entity*, wording is standardized platform-wide and school identity comes through variables. One consequence you should be aware of: since it's one PE registering one body, the DLT portal likely issues **one approved template id that is valid for all schools** — yet the system stores the DLT id per-tenant, so today the operator pastes the same id into every school one at a time. That's tedious at 10+ schools but also gives you flexibility if ids ever diverge (e.g., different sender headers per school later).

**"There should be a way to create SMS templates for the super admin"** — today: no runtime creation, by design. New template = new `CatalogTemplate` entry in code + PR + run the sync CLI. The spec's rationale is that a body must exactly match what's registered on the DLT portal, and code review is the guardrail against drift. A runtime "create template" screen for the super admin wouldn't violate the single-PE model (schools still wouldn't touch it), but it would move body integrity from code review to a UI — that's the real trade-off to discuss, and it connects to your DLT-format concern.

**"Assign a particular template to a particular school"** — this partially exists already, at the *mapping* level rather than the template level. Every school already has all templates (per-tenant rows); the per-school knob is `notification_mappings`: which template fires for which event, per school. The backend for this is complete (`GET/PUT/DELETE /api/v1/communication/notification-map`, `communication/router.py:111-141`) — and notably it's gated on tenant-side `settings:update`, meaning it was built for the **school admin**, not the super admin. But **no UI consumes it** — nothing in the frontend calls `notification-map` or the tenant-side `/templates` endpoint. So "assignment" exists as a dark feature.

**"Cluttered home page / should be under Communication in the side menu"** — confirmed: the platform console is a single `TenantsPage` with the SMS templates section appended below the tenant list (`TenantsPage.tsx:15`). There's no side-menu structure in the platform console at all — it's one page. A restructure would be purely presentational; no backend change needed.

**"DLT format changes need code changes"** — correct, and it's two coupled places: the body string in the catalog, and the `variables` tuple which must stay a subset of what dispatch call sites actually pass (the strict SMS validation depends on this). Agreed on parking it.

## Summary of who can do what today

| Action | Who | Where |
| --- | --- | --- |
| Create/change template body | Developer only | Code + PR + sync CLI |
| Set DLT id, activate/disable per school | Super admin | Platform console |
| View template names/statuses | School admin | API only — no UI |
| Repoint event → template per school | School admin (by permission) | API only — no UI |
| Tenant-side template editing | Nobody | Explicitly out of scope (single-PE) |

The most interesting finding for your discussion: the per-school assignment mechanism you're asking for already exists in the backend as notification-map overrides, was designed for school admins, and just lacks a screen. The open product questions are (a) whether template *creation* should move from code to a super-admin UI given the DLT-drift risk, and (b) whether mapping overrides should be a school-admin surface (as the permissions suggest) or a super-admin one (as your framing suggests).

## Assistant (2026-08-05T05:52:27)

Here's a concrete walk-through using a real event from the code.

## The default (no overrides)

The code ships with `DEFAULT_MAP` (`service.py:69`), which says for each event, which template to use on each channel:

```python
"fees.payment.recorded": {
    "sms":      "payment_received",
    "whatsapp": "receipt_issued",
    "email":    "receipt_attached",
},
```

So when a clerk records a fee payment at **Greenwood School**, the dispatcher fires the event `fees.payment.recorded`, looks it up in this map, and sends three messages to the parent:

- SMS using the `payment_received` template → "Payment of Rs 5000 received via UPI. Thank you."
- WhatsApp using `receipt_issued`
- Email using `receipt_attached`

Every school gets this same behavior out of the box. Nothing is configured anywhere — it's just the code default.

## An override (per school)

Now suppose Greenwood says: "don't SMS parents on every payment, it costs money — WhatsApp is enough." A row is written into **Greenwood's own** `notification_mappings` table:

```
event = "fees.payment.recorded", channel = "sms", is_active = false
```

Resolution (`resolve_effective`, `service.py:113`) works like a simple two-layer lookup: start with the defaults, then apply that school's override rows on top:

```
defaults:   sms → payment_received,  whatsapp → receipt_issued,  email → receipt_attached
override:   sms is disabled                    (Greenwood only)
result:                              whatsapp → receipt_issued,  email → receipt_attached
```

Greenwood parents now get WhatsApp + email only. **Riverside School has no override row, so it still gets all three.** Each school's overrides live in that school's own database, so they can never affect another school.

## The other kind of override: repointing

Instead of disabling, an override can swap which template is used. Say a second SMS template `payment_received_hindi` existed. Greenwood's override row would be:

```
event = "fees.payment.recorded", channel = "sms", template_id = <id of payment_received_hindi>
```

Now on payment: Greenwood sends the Hindi SMS, every other school still sends the default English one. Same event, same trigger point in code — only the template lookup changed for that one school.

That's the entire mechanism: **defaults in code, exceptions as per-school rows, exceptions win.** This is exactly the "assign a particular template to a particular school" capability you asked about — it just has no UI yet (the API is `GET/PUT/DELETE /api/v1/communication/notification-map`).

One catch that matters for your plan: repointing only helps if an alternative template exists, and today templates only come from the code catalog. So the assignment mechanism is ready, but the "create a school-specific template" step in front of it is what's missing.
