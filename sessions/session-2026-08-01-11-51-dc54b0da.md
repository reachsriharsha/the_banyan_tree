## Your question: does the school need its own Razorpay login?

**Yes — and it's not optional.** The design is deliberately one-Razorpay-account-per-school:

- Money goes **parent → the school's own Razorpay account → the school's own bank account**. Akshara never holds funds and has no shared/platform Razorpay account.
- Akshara stores **that school's** Key ID, Key Secret, and Webhook Secret in the school's own tenant database (`docs/specs/m3_09_online_payments/design.md:5`), and constructs the Razorpay client per request from them — nothing lives in env vars.
- The webhook URL itself carries the school slug: `/api/v1/public/webhooks/razorpay/<slug>` (`backend/app/modules/fees/webhook_router.py:44`), precisely because each school configures the webhook from its own Razorpay dashboard.

## The three things that most often bite on a first live test

1. **The webhook is mandatory, not a nice-to-have.** Only `payment.captured` arriving at Akshara marks an invoice paid. The browser callback can only reach *awaiting_confirmation* — by design, since UPI reports success in the browser before capture. No webhook = every payment stalls forever at "Awaiting confirmation".
2. **You need the webhook URL from the platform team.** The school slug is never displayed in the school admin UI — it only appears in the platform (super-admin) console. Wrong slug → Razorpay logs a `400` and no payment ever settles.
3. **Saving requires re-entering all three values every time**, even to just flip the enable toggle off (`GatewayConfigCard.tsx:63` requires all three; `GatewayConfigIn` rejects empty strings). Secrets are write-only — the GET returns only booleans. Store them in your own password manager before you paste them.

## Suggested test sequence

Use `rzp_test_…` keys first — they start with `rzp_`, so they hit the real Razorpay API through the real HTTP adapter (`gateway.py:281`), exercising the entire chain including the signature checks. Only keys *not* starting with `rzp_` fall through to the fake, which is the E2E-only path. So a test-mode run is a genuine rehearsal, then repeat Steps 2–4 in Live mode with a small real payment plus a dashboard refund to close the loop.

Also worth knowing before you go live: refunds are raised in the Razorpay dashboard and then entered into Akshara by `rfnd_` id (Akshara doesn't push refunds out), and **Reconcile now** on the same Payment tab is your recovery button if a webhook is ever lost.

## The short version for your run

**Tunnel port 8000, not 5173.** Only the webhook needs to be public — your browser keeps using `localhost:5173`. Tunnelling the Vite server instead hits Vite 6's host check ("Blocked request. This host is not allowed."), which would need `server.allowedHosts` in `vite.config.ts`.

```
ngrok http 8000
```

Webhook URL, with the dev seed's tenant slug:

```
https://<subdomain>.ngrok-free.app/api/v1/public/webhooks/razorpay/demoschool
```

## The one step that silently breaks the test

The dev seed ships `key_id = "fake_demo_key"` (`backend/app/seeds/dev_seed.py:1113`). Any key not starting with `rzp_` routes to `FakeRazorpayGateway` (`gateway.py:281`) — no HTTP call to Razorpay, no Checkout modal, the UI just says "test gateway". You must overwrite it in **Settings → Payment** with your real `rzp_test_…` keys. Because test keys do start with `rzp_`, everything after that is the genuine code path: real API call, real HMAC checks, real webhook.

Related trap: `dev_db recreate --seed` wipes the gateway config back to the fake creds, so seed *before* you save your keys, not after.

## Three surfaces to watch simultaneously

- ngrok inspector at `http://127.0.0.1:4040` — the POST and its response code
- Backend log — `fees.payment.order_created` → `fees.webhook.received` → `fees.payment.captured`
- Parent UI — *Awaiting confirmation* → *Paid* + auto receipt

`fees.webhook.rejected` with `reason: "bad_signature"` = mismatched webhook secret; `"unknown_tenant"` = wrong slug.

## Two drills the setup makes easy

- **Replay** the captured webhook from the ngrok inspector — should return `duplicate: true` and change nothing. Proves the idempotency guard.
- **Kill ngrok, then pay** — the order stalls at *Awaiting confirmation*; press **Reconcile now** and watch it settle from Razorpay's own truth. That's the production recovery path.

One warning worth repeating from the guide: never point a **live-mode** webhook at an ngrok tunnel. Test mode only.
