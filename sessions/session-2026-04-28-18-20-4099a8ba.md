Good instincts on most of this — strict day-1 quality control, lint mandatory, E2E as the definition of "done", clean HTML output for humans. Two things I'd push back on, then a proposal.

**Where "unit tests = waste of time" is half right.** The pattern that's a waste: mocking the DB and asserting a controller returns the row you stuffed in. That's tautology. But this codebase has real pure-function logic where unit tests beat E2E by 100×:

- **Late fee calc** (US-M3-03 in the plan) — slab rules like ₹50 days 1–7, ₹100 days 8–15, ₹200 days 16+. 20+ boundary cases. As E2E that's 20 × ~10s of setup. As pure-function tests that's milliseconds.
- **RBAC matrix** — 30–40 permission keys × 4 roles. Lookup table; trivial to unit-test, painful to E2E.
- **Money math** — `Decimal` partial payments, gap-free invoice serials, currency formatting. The kind of thing where a single off-by-one corrupts production accounts.
- **Excel parser for bulk import** (US-M2-05) — DD-MM-YYYY vs DD/MM/YYYY, accented and Hindi names, trailing whitespace. 30 ugly rows take 30 unit tests.

So my line: **no CRUD pass-through unit tests; ruthless unit tests on pure logic.** That's also exactly what plan §8.1's pyramid says (~400 unit, ~150 integration, ~60–80 E2E).

**The missing middle layer.** Between unit and E2E sits API integration tests using FastAPI's `TestClient` against a real Postgres (the dev compose). They're ~5–10× faster than E2E, give you full HTTP coverage, and don't depend on a browser. For an agent debugging a regression, "run the failing API test" is a tighter loop than "run the full E2E and stare at a 30s trace." Plan §8.1 budgets ~150 of these.

**Layered = faster feedback for agents, not more bureaucracy.** When a Playwright spec fails, "the entire stack might be broken" is hard to triage. When the failure is `tests/unit/test_late_fee.py::test_slab_boundary_day_8`, the agent knows where to look. Pure-E2E means slow feedback and ambiguous diagnosis.
