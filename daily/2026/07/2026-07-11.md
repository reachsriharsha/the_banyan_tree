## Session 1 — Parent RBAC Over-Grant Analysis

**Project:** Akshara (School Management)

**Issue:** Parent user sees full admin student roster instead of only their own children

**Analysis (No Code Changes):**
- Parent role illegitimately holds admin-plane keys: `students:read`, `fees:read`, `attendance:read`, `communication:read`, `circulars:read`
- These keys date back to m1_09 RBAC matrix (47fb2ab), before self-scoped parent keys existed
- Parent can see full roster + export CSV (both endpoints gate on `students:read`)
- Same pattern likely applies to other admin surfaces (/admin/fees, /attendance, /communication, /circulars)

**Severity:** Broken access control / tenant-wide PII disclosure

**Root Cause Chain:**
1. Sidebar shows Students/Fees/Attendance/Communication/Circulars to anyone with those broad keys
2. Frontend router `/admin/students` has no parent-specific guard; backend is "the real authority"
3. Backend endpoint `GET /api/v1/admin/students` requires only `students:read`, no row-level scoping

**Dependency Check:** Verified all parent-facing functionality uses ONLY `/api/v1/parent/*` endpoints, which gate on self-scoped keys (`parent:children:read`, `parent:fees:pay`, `parent:prefs:write`). Safe to remove broad keys.

**Fix Plan:** Spec PR #241 (`m1_09_parent_rbac_scope`) created via Vishwakarma workflow
